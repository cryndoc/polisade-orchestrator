# /polisade:migrate — Schema Migration

Обновляет PROJECT_STATE.json и knowledge.json до текущей версии схемы. Добавляет недостающие поля, создаёт artifactIndex, устанавливает schemaVersion. Также добавляет `testing.strategy` в knowledge.json если отсутствует.

VCS bootstrap: если `settings.vcsProvider` отсутствует — добавляет `"github"`. Если PM вручную переключил провайдер на `bitbucket-server` — создаёт `.env.example` (reference) и `.env` (stub для заполнения токенов) из plugin templates, добавляет некомментированную `.env` в `.gitignore`. Заполненный `.env` не перезаписывается (идемпотентность). ⚠️ Под GigaCode Filesystem Guard сам скрипт миграции может не запуститься (install-dir read-protected) — тогда `.env`/`.env.example` автоматически не появятся; PM создаёт `.env` вручную из `.env.example` (`cp .env.example .env`) и заполняет токены.

## Использование

```
/polisade:migrate            # Dry-run — показать что изменится
/polisade:migrate --apply    # Показать diff и применить после подтверждения
/polisade:migrate --enable=changeSpec --apply    # Включить режим
/polisade:migrate --disable=designCorpus --apply # Выключить (переключатель)
/polisade:migrate --show-template-diff           # Чем шаблоны проекта разошлись с каноном
/polisade:migrate --adopt-templates=all --apply  # Принять канон шаблонов
```

Экспериментальные режимы включаются **командой, а не правкой JSON руками**.
`--enable=<флаг>` / `--disable=<флаг>` (через запятую —
несколько) пишут `settings.experimental` тем же путём, что и любая другая
миграция: значит попадают в план dry-run, в `stage_paths` и в коммит.
Несуществующий флаг и опечатка в самой опции — **отказ** со списком
доступных, а не тихое умолчание. Повторное включение — no-op.

   записи до ручной правки и повторного запуска. `--apply` сейчас запрещён.

   `pm_questions` вида `artifact-status-decision` — план ручного разбора,
   а не разрешение на переписывание. Прочитай артефакт и источник решения:
   прежние `cancelled`/`not_actual` не становятся `done`, а ADR

   (`next_steps`) это следующий шаг PM, а не украшение отчёта: режим, который
   он только что включил, сам ничего не делает. Маршрут лежит и в файле
   отчёта, и в состоянии (`.state/pm-reports/migrate.latest.json`), его
   читает `/polisade:doctor`. Маршрута в JSON нет — значит режим выключен и
   шага нет; выдумывать его нельзя.

## Формат вывода

`polisade_migrate.py` всегда печатает **один** JSON-документ на stdout
(контракт OPS-108 — `json.loads(stdout)` обязан проходить). PM-friendly
сообщения и подтверждение интерактивного prompt'а уходят на stderr.
Полная таблица контрактов — `docs/config-reference.md` § Script JSON
output contracts.

### Блок `ОТЧЁТ ДЛЯ PM`

На stderr (и тем же значением в поле `pm_block`) скрипт печатает готовый
отчёт PM между линейками `═`: статус прогона, сводку и пронумерованный
маршрут. Строки внутри блока — те же байты, что в полях `summary` и
`next_steps` того же прогона; блок собран из них, а не написан рядом вторым
текстом. Маршрута в блоке нет, когда режима живого корпуса нет: тогда его нет
и в ответе PM.

Тот же блок, байт в байт, скрипт кладёт файлом в `.state/pm-reports/`
(новый файл на каждый прогон, в git не попадает) и печатает под блоком
готовую строку с путём. В JSON это поле `pm_report`: `status`
(`written` / `failed` / `skipped`), `path`, `sha256` и `line` — ту самую
строку. Дословного копирования блока от тебя больше не ждут: PM получает
итог из JSON и путь к файлу, а полный отчёт открывает там.

### Если схема актуальна

```json
{
  "status": "up_to_date",
  "schemaVersion": 7,
  "polisadeVersion": "3.0.0",
  "touched_paths": [],
  "stage_paths": []
}
```

### Если нужна миграция (dry-run)

```json
{
  "status": "migration_needed",
  "current_schema": 3,
  "target_schema": 6,
  "migrations": [
    "Update schemaVersion: 3 → 7",
    "Add settings.debt.autoCreateTask: true (preserve legacy auto-TASK behavior)"
  ],
  "touched_paths": [".state/PROJECT_STATE.json"],
  "stage_paths": [".state/PROJECT_STATE.json"],
  "dry_run": true
}
```

### После `--apply --yes`

```json
{
  "status": "applied",
  "schemaVersion": 7,
  "applied_count": 2,
  "migrations": ["Update schemaVersion: 3 → 7", "..."],
  "touched_paths": [".state/PROJECT_STATE.json"],
  "stage_paths": [".state/PROJECT_STATE.json"]
}
```

`touched_paths` — всё, что миграция тронула (для информации и для
diff-сверки с `git status --porcelain`).

`experimental_modes` — состояние каждого режима: значение,
инертность, что цикл будет делать и **чего режиму не хватает в проекте**
(`requires[].status`: `ok` / `will-arrive` — привезёт этот же прогон /
`missing`). Показать PM целиком: включённый режим, которому не хватает
шаблона, — это не «всё готово» (класс F1). В dry-run печатается ТЕКУЩЕЕ
состояние; что изменится, говорит список `migrations`.

`requires` называет не только файлы: элемент с ключом `command` и статусом
`unavailable` означает, что не хватает **самой команды** — её нет в сборке под
эту цель (`experimental_modes.<флаг>.target`), и режим с `available: false`
включать нечему. Процитируй `reason` дословно; не переписывай его в «нужно
что-то доустановить». Явный `--enable` такого режима скрипт отклоняет
(`status: refused`, rc=2) — это отказ, а не сбой.

`next_steps` — **готовые строки следующего шага**, они же строки маршрута
внутри блока `ОТЧЁТ ДЛЯ PM`. Это маршрут «включил → построил → перевёл силосы
→ сверил» для PM, который только что включил живой корпус ЭТОЙ же командой.
Ключевое утверждение маршрута — **корпус не строится сам**; если ты
пересказываешь его своими словами, ты пересказываешь его неверно (замерено —
из строк устойчиво исчезала именно объясняющая половина). Список пуст — значит
режим выключен и маршрута нет; тогда не выдумывай его.

⛔ **`design_silos` — три формы, не две**. Пустой `design_silos`
сам по себе НЕ означает «силосов нет»: он заполняется только под
`--migrate-design`. Что говорить PM, решает `design_silos_status.status`:

| `status` | что это значит | что печатать |
|---|---|---|
| `not-analyzed` | силосы на диске ЕСТЬ (`found`, `silos`), но миграция их интента не запрашивалась | «найдено пакетов: N (перечислить); их интент НЕ анализировался — нужен прогон с `--migrate-design`» |
| `none` | пакетов DESIGN-NNN в проекте нет | «силосов нет — переводить на корпус нечего» |
| `analyzed` | прогон был с `--migrate-design` | разбор по каждому пакету — из `design_silos` |

Никогда не докладывай «силосов, по-видимому, нет» по пустому списку: это
ровно та ошибка, ради которой заведён `design_silos_status`.

`stage_paths` — subset для `git add`: исключает пути, которые после
миграции попали под `.gitignore` (например `.env` при bitbucket bootstrap
оказывается в `touched_paths`, но НЕ в `stage_paths`, потому что та же
миграция добавила `.env` в `.gitignore` — попытка `git add .env` дала
бы rc=1).

`pr_body` — появляется только при `--pr-body=<путь.md>`:
`{"path": ..., "status": "written"}`, `{"status": "failed", "detail": ...}` либо
`{"status": "skipped", "detail": ...}` — на любом `--apply`, который не был
подтверждён (и при ответе «нет», и при отказе за отсутствием человека).
Указанная опция, не давшая файла, обязана быть НАЗВАНА, а не исчезнуть из ответа.
Тело PR собирает ИНСТРУМЕНТ из этого же отчёта (сводка, миграции, пути,
вопросы PM, режимы), поэтому в PR попадает то, что раньше оставалось в
консоли. `failed` называется в теле PR прямым текстом.

### Дифф шаблонов (`--show-template-diff`)

Отдельный статус `template_diff` и отдельный документ: `canonical_source`
(откуда прочитан канон), `templates[]` с полями `name`, `state`
(`diverged` / `same` / `absent` / `symlink` / `unreadable`), `added`,
`removed`, `diff`, плюс `diverged[]` и `summary`. Ничего не пишет и не
планирует; `touched_paths` и `stage_paths` пусты. Дифф печатай как есть — его
собрал инструмент.

### Если derived list содержит неверный тип (rc=2)

`status: invalid_derived_lists` содержит `issues[]` с путями вида
`inReview[0]`, ожидаемым и фактическим типом, а также `action` с порядком
ручного восстановления. `touched_paths` и `stage_paths` пусты. Ни dry-run,
ни apply не изменяют файлы; миграция не сообщает `up_to_date` или `applied`.

## Важно

- **По умолчанию dry-run** — проект не меняется без `--apply`; пишется только
  файл отчёта для PM в `.state/pm-reports/` (локальный, в git не попадает)
- **Никогда не трогает `artifacts`** — только создаёт новый `artifactIndex`
- **Доносит шаблоны артефактов** (`docs/templates/*`). Скиллы
  читают шаблон ИЗ ПРОЕКТА, а не из плагина, поэтому проект, приехавший со
  старой версии, упирался в отсутствующий файл — `change-spec-template.md`
  после включения `changeSpec` тому пример. Правило троичное и несимметричное:
  шаблона нет — добавляется; совпал (с точностью до концов строк) — тишина;
  **отличается — вопрос PM, никогда не перезапись**: правка шаблона командой
  это источник, а не производная. Что именно разошлось, видно в `pm_questions`
  (`docs-template-diverged:<имя>`); решение за человеком.
- **У вопроса о расхождении есть выход**. Он называет ТРИ вещи,
  без которых решение принять нельзя: сколько строк добавил бы и убрал бы
  переход на канон, по какому адресу канон прочитан ИМЕННО в этом прогоне
  (вендорённый набор проекта разрешается первым — под Filesystem Guard каталог
  установки нечитаем), и команду, которой канон принимается. Дифф печатает
  ИНСТРУМЕНТ: `--show-template-diff` (все разошедшиеся) либо
  `--show-template-diff=<имя.md>`; это диагностика, она ничего не пишет.
  Принятие — `--adopt-templates=<имя.md,…>` или `=all`: **обычная миграция**,
  то есть план dry-run, `stage_paths`, коммит. Без флага поведение прежнее,
  молчаливой перезаписи нет; повторный прогон после принятия — no-op.
  Несуществующее имя шаблона — **отказ** (rc=2) со списком доступных, а не
  молчаливый пропуск; неузнанное написание опции про шаблоны — тоже отказ.
  До этого PM получал в корп-прогоне девять одинаковых абзацев «решение за
  человеком» и ни одной зацепки, а агент дальше искал канон обходом каталога
  установки и копировал файлы руками мимо плана и коммита.
- Безопасно запускать повторно — идемпотентная миграция
- После миграции `/polisade:doctor` должен показывать pass для state_schema

**Why этот рецепт жёсткий:**

- `polisade_vcs.py git-push` верифицирует push (exit-code + pattern-scan +
  SHA), bare `git push` — нет.
- `--body-file` обходит ограничение корп-шелла на command substitution.
- `polisade_vcs.py pr-scope` считает состав PR **против удалённой базы**
  (`git ls-remote`, а не локальный `origin/<base>`, который сам бывает
  несвежим) и отдельно называет `inherited` — коммиты, достижимые ещё и с
  локальной `refs/heads/<base>`, то есть бывшие там ДО этой ветки. Это
  механическое определение «не моё»: оно не требует ни памяти о сессии, ни
  догадки об авторстве. Зачем: `git switch -c` режет от того, чем оказалась
  локальная база, и если она впереди удалённой, те коммиты въезжают в PR
  молча — все остальные проверки рецепта смотрят в рабочее дерево, а не в
  историю. Замерено на корп-миграции 17.09.2026: vendor-коммит сидел на
  локальной `main` впереди `origin/main`, ветка нарезана поверх него, и оба
  проверяющих назвали это «базой ветки, действий не требует». Скрипт только
  читает: он никогда не ребейзит, не сбрасывает и ничего не выбрасывает —
  включать унаследованный коммит в этот PR или изолировать, решает PM.
- Самодельный Python/curl в Bitbucket/GitHub REST API утекает токены из
  `.env` мимо `polisade_vcs.py` и теряет provider-agnostic мост.
- `git status --porcelain` — fallback, не primary: при параллельных
  user-edits даёт лишние файлы.
