Polisade Orchestrator — плагин для CLI-агента, который помогает пройти путь от требований до изменений в репозитории. Он сохраняет требования, проектные решения и задачи в файлах, затем ведёт работу по циклу реализация → тесты → PR → ревью → слияние. Глубину проработки и степень автономности выбирает команда. Инструкции и Python-скрипты доступны в публичном репозитории.

Модель процесса

Что это и на чём держится

Работа сохраняется в файлах репозитория: у требований и задач есть идентификаторы, связи и статусы. По ним агент определяет, что можно делать дальше и где требуется решение человека.

1. Артефакт вместо переписки

Идея превращается в файл в репозитории: FEAT-бриф, PRD, SPEC, DESIGN-пакет, PLAN, TASK. Файл видно в code review, он мержится вместе с кодом и живёт между сессиями агента.

2. Исполняется только TASK

PRD, SPEC, PLAN нужны, чтобы договориться. Реализация всегда сходится к TASK-NNN — атомарной единице с координатами правки, критериями приёмки и трассировкой на требование.

3. Готово ≠ «код написан»

Задача закрывается только после полного цикла: регрессия проекта, PR, независимое ревью с оценкой, merge. Один коммит — это ещё не done.

Три вида работы внутри одного цикла

Полезно всегда понимать, кто именно выполняет шаг — от этого зависит, чему можно доверять без проверки.

КтоЧто делаетЧем это ценно
человек Формулирует интент, отвечает на вопросы, выбирает глубину проработки, подтверждает критерии приёмки, мержит вручную в контролируемом режиме. Решения, которые нельзя домыслить.
модель Пишет и обновляет артефакты, декомпозирует работу, реализует код и тесты, чинит замечания ревью. Объём работы.
скрипт Линт артефактов и спецификации, приёмочный прогон, синхронизация состояния, миграции схемы, операции с PR, диагностика, проверка дрейфа документации. Повторяемость конкретной проверки при одинаковых входных данных.

Все скрипты — Python 3 на стандартной библиотеке, без внешних зависимостей: их можно запускать локально и в CI при наличии нужного окружения.

Термины, которые встретятся дальше

Ничего экзотического, но слова используются в узком смысле — стоит сверить понимание один раз.

ТерминЧто значит здесь
CLI-агентПрограмма-помощник, которая работает в терминале и умеет читать и править файлы проекта, запускать команды, ходить в git. Polisade — не самостоятельное приложение, а набор инструкций для такого агента; графического интерфейса у него нет.
PR (pull request)Заявка «влейте мои изменения в основную ветку». Место, где коллеги смотрят дифф, оставляют замечания и одобряют работу.
Ветка · merge · диффВетка — отдельная линия работы, чтобы не мешать другим. Merge — вливание её в основную. Дифф — построчный список того, что изменилось.
ЛинтАвтоматическая проверка формы: не смысла, а того, что документ или код оформлены по правилам (есть обязательные разделы, ссылки разрешаются, нет запрещённых конструкций).
РегрессияПрогон всех тестов проекта, а не только новых, — чтобы убедиться, что свежая правка не сломала соседнее.
ИнтентИсходная формулировка «что нужно» человеческими словами, до всякой формализации.
АртефактФайл в репозитории, несущий одну единицу смысла: бриф, спецификация, план, задача, решение. Не сообщение в чате.
Семя (seed) · номерДва имени одного артефакта. Семя (TASK-k7m2q4xz) генерируется при создании на любой машине и не меняется никогда. Номер (TASK-007) выдаёт /polisade:sync --apply и только на основной ветке. Зачем так — в разделе про артефакты.
СкиллФайл-инструкция одной команды (skills/<имя>/SKILL.md). Открытый текст — можно прочитать, какие действия предписаны команде, до того как её запускать.
FEAT · BUG · DEBT · CHORE · SPIKEТипы первичных входов: фича, дефект, техдолг, служебная задача, исследование. Каждому выдаётся ID вида FEAT-001.
PRD · SPEC · DESIGN · PLAN · TASKСтупени формализации: продуктовый документ → техническая спецификация → пакет архитектурных документов → план по фазам → атомарная исполняемая задача.
FR · NFRНумерованные функциональные и нефункциональные требования внутри спецификации (FR-003). На них ссылаются задачи, ревью и приёмка — это и есть трассируемость.
Локализация (LOCALIZE)Обязательный шаг перед правкой кода: список целей «файл + символ + зачем», полученный поиском по исходникам.
КоординатыТе же цели, но записанные в задачу заранее: файл и символ, которые она имеет право менять.
Дизайн-пакетКаталог архитектурных документов на одну спецификацию: C4-схемы, диаграммы последовательностей, модель данных, API, ADR.
ADRЗапись архитектурного решения: контекст, выбор, последствия. Чтобы через полгода не переспорить то же самое заново.
Приёмочная пара (AC)Описание ожидаемого результата и одна команда, которая его проверяет.
Источник утвержденияУказание, откуда взято утверждение (например «найдено поиском по коду»), чтобы догадка не выглядела как проверенный факт.
best-effortРезультат, который инструмент формирует по доступным данным без гарантии полноты и правильности. Его нужно оценить с учётом указанных ограничений.
advisoryПроверка, которая сообщает о проблеме, но не блокирует работу.
ДрейфРасхождение документации и кода: документ говорит одно, реализация давно делает другое.
worktreeВторой рабочий каталог того же git-репозитория. Позволяет вести задачу изолированно, не переключая вашу основную ветку.
checkpoint · design gateНамеренная остановка процесса, чтобы человек выбрал глубину проработки или подтвердил, что дизайн-пакет не нужен.

Размер S · M · LОценка объёма первичной работы, которую ставит feature. На M и L он предлагает добавить спецификацию (для L — начать с PRD).
PASS · IMPROVEВердикт ревью: оценка 8 и выше — PASS (можно мержить), ниже — IMPROVE (доработка и повторное ревью).
C4Способ рисовать архитектуру четырьмя уровнями детализации (контекст → контейнеры → компоненты → код). В дизайн-пакете используются первые три.
JTBD«Jobs to be done» — раздел PRD про то, какую работу пользователь пытается сделать, а не про список функций.
waiverФайл в docs/waivers/, которым человек осознанно разрешает расхождение (например «здесь документация отстаёт намеренно, вот почему»).
СубагентОтдельный изолированный запуск модели с собственным контекстом. Используется, чтобы ревью не видело «мыслей» реализации.

С чего начать

Быстрый старт

Если вы читаете это по дороге к решению «пробовать или нет» — вот минимум. Подробная картина начинается со следующего раздела.

Что нужно иметь

  • Репозиторий под git (git 2.25 или новее) и доступ к GitHub или Bitbucket Server — цикл заканчивается PR.
  • Один из CLI-агентов — Claude Code, Qwen CLI, GigaCode CLI или opencode — со своим доступом к модели. Плагин не содержит ни модели, ни ключей: он даёт процесс, а «думает» ваш агент на вашей подписке.
  • Python 3 — на нём детерминированные скрипты (линты, приёмка, диагностика). Сами скрипты используют стандартную библиотеку; зависимости вашего проекта устанавливаются отдельно.
  • gh с авторизацией — для операций с PR на GitHub; для Bitbucket Server — токен в .env.
  • Опционально Codex CLI — единственный поддерживаемый внешний ревьюер: с ним ревью делает не тот же агент, который писал код.

Шесть команд, которых хватает

/polisade:init MyProject     # каркас: .state/, docs/, backlog/, tasks/
/polisade:init-verify        # структура создана, а не «сочинена» моделью

/polisade:feature "Нужен экспорт отчёта в PDF"
/polisade:tasks FEAT-001     # разложить в атомарные задачи
/polisade:continue           # код → тесты → PR → ревью → merge

/polisade:state              # где мы находимся (главный обзор)

В поставке 27 команд; эти шесть показывают основной маршрут. Следуйте вопросам агента: изменение API или данных может потребовать spec до создания задач. Остальные нужны по случаю: spec и design для сложной работы, unblock когда агент задал вопрос, doctor и sync для обслуживания.

Команды можно не запоминать

Агент распознаёт намерение по обычной фразе и сам вызывает нужный сценарий. Таблица ниже — для Claude Code, где маршрутизация описана в файле правил проекта; в сборках Qwen, GigaCode и opencode фразами доступна только часть команд, остальные вызываются слешем напрямую:

Вы говоритеЧто произойдёт
«Статус?»state — обзор проекта
«Кнопка не работает»defect — регистрация дефекта
«Нужен экспорт в PDF»feature — бриф фичи
«Новый модуль аналитики»prd — продуктовый документ
«Надо отрефакторить»debt — запись техдолга
«Работай»continue — автономный цикл
«Что ждёт моего ответа?»unblock — вопросы к вам

Если намерение неоднозначно, агент обязан спросить, а не угадать.

Чем это не является

  • Не приложение с интерфейсом. Вся работа идёт командами в терминале — своими или продиктованными агенту обычной фразой. Экранов, кнопок и веб-панели нет; если вы не работаете в терминале, вам понадобится кто-то из команды рядом.
  • Не SaaS и не сервис. Всё выполняется локально вашим агентом, артефакты остаются в вашем репозитории, телеметрии у плагина нет (телеметрия вашего CLI-агента и внешнего ревьюера — вопрос к их поставщикам). Сеть используется там, где это видно: операции с PR, проверка доступа в doctor, верификация push, запуск внешнего ревьюера и — если вы дали ссылки в интервью PRD — их загрузка.
  • Не модель и не подписка. Доступ к LLM — ваш; плагин не проксирует запросы и не хранит ключи.
  • Не замена CI — но и не «пишите тесты сами». Тесты по задаче агент пишет и запускает сам (по умолчанию сначала красный тест, потом код), регрессию проекта гоняет после каждой задачи. CI нужен для другого: чтобы те же проверки исполнялись независимо от агента, в чистом окружении и как обязательная проверка PR. Подробно — в разделе «Команда, трекер, CI».
  • Не интеграция с трекером. Единица работы — файл в git; связь с Jira или Issues поддерживается ссылкой (см. раздел «Команда, трекер, CI»).
  • Не автопилот без человека. При недостатке сведений процесс останавливается и спрашивает — это заложено намеренно.

Скорее не для вас, если

  • У вас GitLab. Поддерживаются GitHub (включая Enterprise) и Bitbucket Server; GitLab — нет.
  • В репозитории нет тестов. Регрессия и приёмка — опора всего цикла; без них отсутствует исполняемая проверка поведения проекта.
  • Нужен доказуемый, аудируемый результат. Инструмент даёт практики, линты и трассируемость, но не машинные гарантии — что именно не гарантируется, разобрано в разделе «Границы и ограничения».
  • Код нельзя передавать дополнительному инструменту. Независимое ревью отдаёт дифф другому CLI; если это неприемлемо — остаётся режим self (агент проверяет сам себя) или ручное ревью.
  • Вы ждёте автопилот без участия человека. Процесс намеренно останавливается и задаёт вопросы.

Если вы продакт или руководитель — короткая версия

Дальше по документу много терминала. Здесь то же самое без него.

Что меняется в работе

Задача перестаёт быть строчкой в трекере и становится набором файлов в репозитории: бриф, спецификация, задачи. Их можно проверять и хранить в тех же PR, что и код. Вы формулируете работу словами, отвечаете на вопросы, когда агент останавливается, и решаете, что считается сделанным.

Что решаете лично: нужна ли спецификация, нужен ли архитектурный пакет, что означает «готово» (образ результата подтверждаете по одному пункту), кто мержит, и что делать, если ревью дважды не сошлось.

Что спросят у вас в компании

  • Куда уходит код. В модель вашего CLI-агента; при независимом ревью — во второй инструмент, который сам решает, какие файлы прочитать. Режим self исключает дополнительный CLI; основной агент продолжает обращаться к своей модели.
  • Что с правами. Плагин не создаёт собственную песочницу; права задаются CLI и средой, а список разрешений Claude Code широкий — раздел «Права и аудиторский след» написан специально для этого разговора.
  • Чего нет. GitLab не поддерживается. Интеграции с трекером нет (кроме ключа задачи в имени файла спецификации). Под Windows — через WSL.
  • Что нужно от команды. Репозиторий на GitHub или Bitbucket Server, работающие тесты и один человек, готовый отвечать на вопросы агента в течение дня.

С чего начать пилот: одна средняя фича, один инженер, режим с остановкой перед merge. Оцените пилот по принятым в команде показателям: сколько задач дошло до слияния без переделки, сколько потребовалось вмешательств и какие дефекты обнаружены после проверки. Затраты измерьте на первой задаче по отчётам CLI и CI: они зависят от модели, объёма контекста, числа итераций и используемой инфраструктуры.

Что это стоит. Плагин распространяется под лицензией Apache 2.0. Затраты на модель, внешнее ревью, CI и инфраструктуру зависят от выбранных инструментов. Длительность и стоимость лучше измерить на первой задаче своего проекта: существенную часть расходов могут дать формализация и повторные проверки.
Установка

Установка и доступы

Выберите сборку для своего CLI. В Claude Code, Qwen и GigaCode команды имеют вид /polisade:<имя>, в opencode — /polisade-<имя>. Ниже ссылки закреплены на проверенной версии v3.8.15; новые выпуски доступны на странице релизов.

Claude Code

/plugin marketplace add cryndoc/polisade-orchestrator
/plugin install polisade --scope project
/polisade:init MyProject

Маркетплейс подключается один раз. Установку и инициализацию проекта выполняйте из своего репозитория. Маркетплейс устанавливает доступную в нём версию; сверяйте её с версией этого руководства.

Qwen CLI

mkdir -p ~/.qwen/extensions
curl -fL https://github.com/cryndoc/polisade-orchestrator/releases/download/v3.8.15/polisade-qwen.zip -o /tmp/polisade-qwen.zip
unzip /tmp/polisade-qwen.zip -d ~/.qwen/extensions/
qwen
/polisade:init MyProject

GigaCode CLI

mkdir -p ~/.gigacode/extensions
curl -fL https://github.com/cryndoc/polisade-orchestrator/releases/download/v3.8.15/polisade-gigacode.zip -o /tmp/polisade-gigacode.zip
unzip /tmp/polisade-gigacode.zip -d ~/.gigacode/extensions/

У этой сборки есть дополнительный шаг: из корня своего проекта, в обычном терминале выполните:

bash ~/.gigacode/extensions/polisade/setup-project.sh

Скрипт копирует рабочие файлы в .polisade/bin/ и сверяет их с манифестом. В v3.8.15 манифест содержит 78 файлов. Закоммитьте копию вместе с проектом, затем запустите GigaCode:

gigacode
/polisade:init MyProject
/polisade:init-verify

Копия в проекте нужна из-за ограничений доступа к каталогу расширения. После каждого обновления повторяйте setup-project.sh и коммитьте обновлённую копию. Скрипт заменяет .polisade/bin/, поэтому собственные файлы туда не добавляйте. В сборке GigaCode по умолчанию выбран Bitbucket Server. Если используете GitHub, настройте settings.vcsProvider соответственно.

Обновление существующего проекта. Для v3.8.15 особенно важно обновить копию скриптов: ревью использует новые параметры и два шаблона задания ревьюеру. Старая копия остановит вызов. Выполните setup-project.sh, затем /polisade:migrate для предпросмотра, примените согласованные изменения и запустите /polisade:doctor. Повторный init для обновления не нужен. Проверка doctor сверяет копию с её собственным манифестом и версией состояния проекта; одного зелёного результата недостаточно, если и копия, и состояние остались старыми.

opencode

До распаковки сохраните существующий ~/.config/opencode/AGENTS.md, если он есть: архив содержит файл с таким же именем.

mkdir -p ~/.config/opencode
curl -fL https://github.com/cryndoc/polisade-orchestrator/releases/download/v3.8.15/polisade-opencode.zip -o /tmp/polisade-opencode.zip
unzip /tmp/polisade-opencode.zip -d ~/.config/opencode/
opencode
/polisade-init MyProject

Можно не извлекать глобальный AGENTS.md — команды работают и без него. Команды установки приведены для macOS и Linux; для Windows используйте WSL.

Запуск из скрипта

Для автоматического запуска разрешения на инструменты задаются флагами CLI. Эти флаги расширяют возможности агента; используйте их в окружении с подходящими правами.

qwen --allowed-tools=run_shell_command -p '/polisade:review-pr 21'
gigacode --allowed-tools=run_shell_command --approval-mode auto-edit -p '/polisade:review-pr 21'
opencode run --command polisade-review-pr --dangerously-skip-permissions 21

У Qwen auto-edit само по себе не разрешает shell-вызовы. В рецепте GigaCode используются оба флага. Это отдельные настройки CLI; init не создаёт для Qwen и GigaCode файл разрешений Claude Code.

Перед первым init сохраните текущую работу. Команда копирует шаблоны и правила агента, дополняет .gitignore и устанавливает хук pre-push, если своего хука ещё нет. Файлы с совпадающими именами могут быть заменены. Существующие CLAUDE.md, AGENTS.md, настройки и workflow сначала закоммитьте или сохраните отдельно. После запуска просмотрите дифф и выполните init-verify.

Технический контекст и команда тестов

init пытается определить стек по файлам проекта и заполнить .state/knowledge.json. Команды spec и design уточняют недостающие сведения, реализация может дополнять память по итогам задач. Проверьте найденное: особенно testing.testCommand и доступность окружения из рабочего дерева задачи.

"testing": {
  "strategy": "tdd-first",
  "testCommand": "python3 -m pytest -q",
  "typeCheckCommand": null,
  "lintCommand": null
}

Это фрагмент JSON. Можно сообщить агенту обычной фразой: «Тесты запускаются командой …; запиши её в технический контекст». Если команда не задана, регрессия пропускается с предупреждением. Локальный .venv/ не копируется в git worktree: подготовьте окружение каждого дерева либо используйте доступный ему интерпретатор.

Доступ к репозиторию

GitHub

Нужен авторизованный gh: выполните gh auth login. Поддерживается GitHub Enterprise. Проверяйте доступ командой /polisade:doctor.

Bitbucket Server

Операции выполняются через REST API. В образце конфигурации .env.example описаны URL, токен и способ авторизации; поддерживаются два адреса сервера. Нужная конфигурация выбирается по адресу origin. Проверка — /polisade:doctor --vcs.

Не помещайте реальные токены в коммиты. Строка .env в шаблоне .gitignore закомментирована — проверьте фактическое правило проекта. У polisade_vcs.py есть параметр --env-file для файла вне рабочей копии; он задаётся для конкретного вызова и не распространяется автоматически на все команды плагина. Если выбран такой способ, согласуйте его со всеми вызывающими сценариями.

Для Bitbucket проверяются TLS-сертификаты, перенаправления запросов не выполняются. Свой центр сертификации задаётся через POLISADE_VCS_CA; резервные переменные — SSL_CERT_FILE и REQUESTS_CA_BUNDLE. Поведение GitHub зависит от gh. Подробности — в публичном справочнике конфигурации.

Обновление и удаление

Claude Code обновляется через управление плагинами. Для остальных CLI замените установленную сборку свежим архивом; перед заменой сохраните свои изменения, проверьте состав каталога после распаковки, чтобы в нём не остались файлы прежней версии. Для GigaCode также обновите .polisade/bin/. Затем просмотрите /polisade:migrate, примените согласованные изменения и выполните /polisade:doctor.

Удаление плагина выполняется средствами CLI или удалением его каталога. Документы проекта остаются обычными Markdown-файлами. Если удаляете служебные файлы, сначала проверьте свои изменения в правилах агента, workflow, хуках и .gitignore; содержательные документы в docs/, backlog/, tasks/ и acceptance/ обычно стоит сохранить.

Как выбрать модель

Плагин использует модель, доступную в вашем CLI. Формализация требований и архитектуры особенно зависит от её качества. Начните с небольшой задачи, проверьте точность требований, дифф кода и тестов, затем оцените затраты по отчёту CLI. Узкие задачи и точный технический контекст помогают модели, но не заменяют проверку результата.

Права и следы работы

Какие права получает агент и что сохраняется

Раздел для инженера и владельца среды исполнения. До установки можно прочитать skills/init/templates/settings.json в публичной поставке. Реальные права определяются также CLI и окружением, в котором вы его запускаете.

Список разрешений в Claude Code широкий. Шаблон содержит 97 разрешающих масок и 7 запретов. Он допускает сборку, установку зависимостей, работу с git и другие команды. Просмотрите его и согласуйте с правилами команды: часть действий выполняется без отдельного запроса. В Qwen, GigaCode и opencode действуют собственные механизмы разрешений.

Границы доступа

Плагин сам не создаёт песочницу. Worktree отделяет рабочую ветку и файлы, но не является границей доступа процесса к сети или файловой системе. Возможные ограничения задаются вашим CLI, контейнером, учётной записью и настройками среды.

При внешнем ревью запускается отдельный CLI: он может читать файлы задачи и репозитория в пределах своих прав. Режим self исключает этот дополнительный CLI, но основной агент по-прежнему обращается к своей модели. Проверьте условия обработки данных выбранных инструментов.

Что настроить в команде

  • Права агента и доступ к секретам.
  • Защиту основной ветки, обязательные проверки CI и человеческое одобрение PR.
  • Владельца приёмочных тестов и порядок проверки их изменений.
  • Кто отвечает на вопросы агента и разрешает повтор операции после отказа сервера.

Выбор глубины

Три уровня глубины

Главная ошибка новичка — одна и та же тяжёлая цепочка на любую работу. Уровень выбирается по риску, а не по размеру текста задачи. Номера означают глубину проработки: первый уровень — самый подробный маршрут, третий — самый короткий.

Уровень 1

Крупная инициатива

Новый модуль, интеграция с внешней системой, эпик на недели, несколько стейкхолдеров.

prd → spec → design → roadmap → tasks → continue

Дизайн-пакет здесь практически обязателен: API, схемы данных, состояния.

Уровень 2

Обычная фича

Понятная работа на часы или дни, границы известны.

feature → tasks → continue

Появилась архитектурная неопределённость — добавьте spec между ними.

Уровень 3

Баг, техдолг, служебная задача

Узкая и понятная правка. Дефект и служебная задача сразу получают задачу; техдолг — по умолчанию нет, задача создаётся отдельно (tasks DEBT-001) или включается настройкой.

defect | debt | chore → TASK → continue

Отдельный вход — spike, когда сначала нужно исследование.

Правило выбора одной строкой. Меняются API, схема БД или границы системы → нужен spec. Проблема ещё не распакована и требует договорённости со стейкхолдерами → нужен prd. Всё остальное — feature. PRD на каждую мелочь замедляет поток без выгоды.
Справочник

Справочник команд

В Claude Code, Qwen и GigaCode — /polisade:<имя>; в opencode — /polisade-<имя>. В сборках Qwen и GigaCode часть команд доступна ещё и по обычной фразе («сделай PR», «нужен экспорт в PDF») — агент сам находит нужный сценарий.

Вход и формализация

  • feature — бриф фичи, основной вход
  • defect · debt · chore — баг, техдолг, служебная задача
  • spike — исследовательская задача
  • prd — продуктовый документ через интервью
  • spec — техническая спецификация
  • design — дизайн-пакет (C4, ERD, API, ADR, глоссарий)
  • design-corpus — единый живой корпус экспериментально, все CLI
  • roadmap — план по фазам
  • tasks — декомпозиция в TASK

Исполнение и качество

  • implement TASK-NNN — одна задача под контролем
  • continue — автономный цикл по всем готовым задачам
  • acceptance — образ результата: запись, прогон, ремонт (у скрипта под ней есть и отдельный режим list — показать разобранные пары)
  • review — второе мнение о постановке задачи: достаточно ли она ясна для исполнения. Не переводит задачу в следующий статус; если ветка с реализацией уже есть, дополнительно прогоняет по диффу проверку качества тестов
  • review-pr — независимое ревью PR с оценкой (не путать с review выше: та про постановку задачи, эта про готовый PR)
  • pr — операции с PR: create, list, view, diff, merge, comment, close, whoami, другие подкоманды VCS-инструмента доступны с их параметрами; у merge есть --squash, --delete-branch и --task
  • unblock — ответы на вопросы, снятие блокировок

Обзор и обслуживание

  • state — главный обзорный экран; попутно приводит реестр в соответствие с файлами и сообщает об этом строкой «синхронизировано N артефактов»
  • questions — открытые вопросы по артефактам
  • doctor — диагностика проекта и окружения
  • sync --apply — пересборка состояния из файлов и выдача номеров артефактам на основной ветке (без флага — предпросмотр)
  • migrate — обновление схемы состояния
  • reconcile-docs — сверка документации и кода (best-effort: мнение модели без гарантии полноты)
  • init · init-verify — развёртывание и проверка каркаса
  • lint-skills — служебная, проверяет исходники самих команд в проекте не нужна

Рекомендуемый старт

  1. Установить плагин, выполнить init.
  2. Проверить и дописать knowledge.json.
  3. Пилот на средней фиче: feature → tasks → continue.
  4. Второй прогон посложнее: feature → spec → design → tasks → continue.
  5. Записать образ результата: acceptance author, включить прогон в CI.
  6. Зафиксировать правила команды и работать циклом.

После пилота зафиксируйте подходящий порядок шагов в правилах команды.

У ADR собственные состояния: proposed, accepted, deprecated, superseded и not_applicable. Для замены нужна ссылка superseded_by, для неприменимости — причина.

Где находится актуальный статус. В режиме worktree файл задачи может быть обновлён в дереве её ветки, пока копия основной ветки ещё содержит старое значение. Команды state, unblock и continue используют общий читатель живого состояния задач. Не исправляйте корневой TASK только из-за этого различия. Штатные изменения статуса выполняются через VCS-инструмент; произвольное редактирование файлов всё ещё возможно и не заменяет предусмотренные проверки.
Отмена требует отдельного решения. Отменённая работа не переводится в done и не засчитывается как выполнение требований. Вызов review-pr сам по себе не возобновляет закрытую или отменённую задачу. Инструмент проверки отклонит такой запуск до ревью и merge.

Режимы включаются командой, а не правкой JSON

Переключение выполняется через миграцию: изменение видно в предпросмотре и списке затронутых файлов. Выключение флага не отменяет уже созданные документы и не переносит живой корпус обратно в отдельные пакеты. Можно попросить и словами — «включи change-spec»: агент обязан позвать эту команду, а не редактировать .state/ инструментом записи.

/polisade:migrate --enable=changeSpec            # предпросмотр
/polisade:migrate --enable=changeSpec --apply    # включить
/polisade:migrate --disable=designCorpus --apply # выключить

Опечатка — отказ со списком, а не тихое умолчание:

"detail": "Флага `chngeSpec` не существует. Доступные: changeSpec, designCorpus, intentCorpus, onboard."

В ответе есть блок experimental_modes: про каждый режим — включён ли он, не инертен ли и чего ему не хватает в проекте. Например, change-spec требует шаблон спецификации в docs/templates/; статус will-arrive значит «этот же прогон его привезёт», missing — что включённому режиму работать не на чем. Инертные ключи названы прямо: "effect": "НИЧЕГО: флаг инертен…".

Обновление существующего проекта — сначала коммит. /polisade:migrate --apply поднимает схему состояния и правит файлы: удаляет устаревший ключ настроек, переписывает у требований статус done в accepted, приводит номера требований к трёхзначному виду и составным ссылкам в PRD, спецификациях, брифах и задачах, переносит ADR из docs/adr/ в docs/architecture/decisions/, дописывает .gitignore, а с 3.8.0 ещё и доносит шаблоны артефактов, которых в проекте нет: скиллы читают шаблоны из проекта, и старый проект упирался в отсутствующий файл. Правило несимметричное: шаблона нет — добавляется; совпадает — тишина; отличается — вопрос вам, никогда не перезапись (ваша правка шаблона — источник, а не мусор). Итог печатается готовой строкой, которую считает скрипт, а не модель, — например «Миграций: 15, из них шаблонов docs/templates: 11. Затронуто путей: 13. Вопросов PM: 0.» Бэкапов не делает, отката нет, при сбое возможно частичное применение — поэтому чистое рабочее дерево и коммит до запуска обязательны. Без --apply — только предпросмотр.

Если migrate или sync просит решение человека

Начинайте с предпросмотра. В v3.8.15 применённые изменения ещё не означают успешного завершения: при неразрешённых вопросах инструмент может вернуть код 3 с applied: true. Файлы уже изменены, но коммит, push и создание PR останавливаются до решения человека.

Отдельно проверяются неподтверждённые отмены и решения, которые исчезли из списка вопросов после ручной правки статуса, шаблона или флага. Прочитайте блок «ОТЧЁТ ДЛЯ PM» и выполните предлагаемый маршрут: ответить, явно отложить с причиной либо подтвердить исход. Не повторяйте --apply вслепую. Для прямого вызова Python-скрипта в неинтерактивной среде применение требует --apply --yes; --yes подтверждает запись, но не заменяет содержательное решение.

Полный отчёт сохраняется в .state/pm-reports/. Файл появляется и при предпросмотре, если .state/ уже существует; документы и состояние проекта от этого не применяются.

Проверки, которые можно включить в CI

init копирует в проект скрипт проверки дрейфа и workflow для GitHub. Остальные проверки нужно отдельно обеспечить в окружении CI. У GigaCode рабочие скрипты уже находятся в .polisade/bin/; для других сборок их обычно берут из установленного плагина или закреплённого релиза.

  • Проверка дрейфа — scripts/polisade_drift_gate.py уже лежит в вашем репозитории, зависимостей не требует, умеет --json и --report. Коды выхода: 0 чисто, 1 дрейф, 2 ошибка конфигурации. Готовый workflow тоже кладётся при init, но блокировать он начнёт только когда вы сделаете его обязательным чеком в защите ветки.
  • Остальные проверки — polisade_lint_artifacts.py, polisade_spec_lint.py, polisade_acceptance.py run — работают там, где установлен плагин. Полезные режимы: spec_lint --strict-acceptance поднимает предупреждения об отсутствующей приёмке до ошибок, acceptance run --fail-on-changed роняет прогон, если проверки правились, doctor --traceability возвращает 1 при непокрытых требованиях. Отдельно про приёмку: её база хешей (.state/acceptance-baseline.json) с версии 3.7.15 коммитится, поэтому --fail-on-changed работает и в чистом раннере — есть с чем сравнивать. В проекте, рождённом на 3.7.x, строки-исключения может не быть — тогда база локальна и режим завершится с кодом 2; проверяется одной командой, см. раздел про командную работу.

Трекер: Jira, YouTrack, Issues

Автоматической синхронизации с трекером нет. Рабочие артефакты хранятся в git; связь с внешней задачей команда поддерживает отдельно.

Но одна точка связи в продукте есть: /polisade:spec --story=<КЛЮЧ> кладёт ключ задачи трекера прямо в имя файла спецификации (SPEC-001__ABC-1234__slug.md) и во frontmatter (story:). Смысл именно в имени: внешние проверки читают diff PR как список путей и по нему решают «в этом PR есть спецификация, и она относится к вон той задаче» — не открывая файлов.

Остальное — договорённость команды: ID артефакта в имени ветки и в заголовке PR, а в задаче трекера — ссылка на PR.

CI: где граница с тестами агента

Тесты пишет и гоняет агент — по задаче и регрессию всего проекта. Отдельно «досоздавать тесты для CI» не нужно: в пайплайне запускаются те же самые. CI добавляет ровно четыре вещи, которых у локального прогона нет: независимость (вердикт не со слов агента), чистое окружение, проверку результата слияния, и принудительность — обязательный status check плюс защита ветки.

Часть проверок можно не откладывать до пайплайна: implement вызывает объявленные вами команды (security-скан, совместимость API, миграционные и нагрузочные тесты) сразу после регрессии — контракт простой, «ненулевой код выхода = находка». Что имеет смысл поставить в пайплайн: те же тесты и линтеры проекта, приёмочный прогон, линт артефактов и спецификации, проверка дрейфа (готовый рецепт кладётся при init; его контракт — быть обязательным чеком, а единственное легальное исключение — файл-waiver со сроком).

Ревью агента — не замена вашему: это дополнительное мнение с оценкой, опубликованное в PR.

Защита ветки и обязательное ревью

Инструмент про них не знает. Он доводит задачу до merge и вызывает merge у провайдера; если ветка защищена — требует аппрув человека, обязательные проверки или актуальность относительно основной ветки, — merge просто не пройдёт: вернётся ошибка провайдера. При вызове pr-merge --task задача перейдёт в waiting_pm, а причина сохранится в записи отказа. Повтор операции блокируется до явного признания причины человеком. Если слияние прошло, но удаление ветки не подтверждено, результат тоже требует разбирательства; сначала проверьте фактическое состояние PR на сервере.

Отдельно: агент не ставит аппрув — провайдер не даёт одобрять собственный PR. Поэтому «ревью с оценкой 9/10» и «аппрув в GitHub» — разные вещи: первое живёт комментарием в PR, второе по-прежнему за человеком.

Практический вывод: защита ветки и автономный цикл совместимы, но тогда цикл заканчивается не на merge, а на открытом PR. Это не поломка — это ровно та конфигурация, которую раздел «Границы» и рекомендует для регулируемого контура.

Несколько людей и агентов

Работа идёт в отдельных ветках и worktree: по ветке на родителя в обычном режиме и по ветке на задачу в режиме плана (правило целиком — в разделе про цикл). Дерево задачи определяет инструмент. Перед продолжением проверяйте, кто работает в этой ветке; worktree не служит распределённой блокировкой между разными машинами.

Что из состояния едет в git. Раньше ответ был «ничего»: весь .state/ закрывался целиком, и всё, что команда наживала, оставалось на ноутбуке того, кто это сделал.   .state/acceptance-baseline.json .state/session-log/
Если что-то напечаталось — /polisade:migrate --apply дописывает недостающие строки-исключения (проверено: после него все четыре записи становятся видимы git). Порядок правил при этом — решение человека: возврат, стоящий выше своего исключения, git не применит, и мигратор такие случаи не чинит молча, а отказывается и говорит почему.

Как избежать столкновений номеров. До 3.7.16 номер брался из локального счётчика, и двое могли одновременно занять FEAT-002. Номер выдаётся на основной ветке, а до этого артефакт живёт под постоянным идентификатором. Два несинхронизированных клона всё ещё могут выдать одинаковый номер; после объединения это обнаруживает проверка дубликатов. Как это устроено, разобрано в разделе про артефакты.

Практики

Практики: что работает и что ломается

Делайте

  • Начинайте с /polisade:state. Не понимаете, что дальше — не угадывайте: команда показывает, что готово к работе, что ждёт решения и что заблокировано.
  • Не отмахивайтесь от интервью про технический контекст. Когда spec или design показывает, что знает о стеке, и просит подтвердить — это дешевле всего поправить именно там. Память проекта пополняется по мере работы, но подтверждает её человек; дополнить можно и обычной фразой, без правки JSON.
  • Выбирайте глубину по риску. Меняются API, БД или границы системы — spec обязателен. Есть интеграции, схемы, состояния — не пропускайте дизайн-пакет: без него декомпозиция и ревью заметно слабее.
  • Пишите приёмку до реализации. Пары «интент + чек», написанные заранее, задают цель; написанные после — просто описывают то, что получилось.
  • Первый пилот — на одной средней фиче. feature → tasks → continue, затем один более сложный кейс через spec и design.
  • Зафиксируйте правила команды — для этого есть штатное место. Каталог docs/conventions/ (каркас кладёт init): когда нужен PRD, когда обязателен дизайн-пакет, кто мержит после implement, кто отвечает на вопросы агента, плюс ваши инженерные соглашения. Реализация и ревью читают эти файлы и цитируют применённые правила; плагин их не сочиняет.
  • Смотрите дифф тестов как обычный код. Особенно в PR, где менялись приёмочные или существующие проверки.

Не делайте

  • Не пытайтесь «исполнить» PRD, SPEC или PLAN. Исполняется только TASK; остальное — договорённости.
  • Не пропускайте спецификацию на изменениях API и схемы данных. Сэкономленные полчаса возвращаются переделкой.
  • Не заводите PRD на каждую мелочь. Это замедляет поток без выигрыша в качестве.
  • Не считайте задачу готовой после коммита. done — это после регрессии, PR и ревью.
  • Не выключайте ревью «на время». Режим off — это осознанное снижение планки, а не ускорение.
  • Не давайте одной задаче расползаться. Список целей локализации вырос в полтора раза — это сигнал переразбить задачу, а не «дописать по ходу».

Зачем нужны два идентификатора

Постоянный идентификатор позволяет ссылаться на документ ещё до слияния. Читаемый номер выдаётся при синхронизации на основной ветке. .state/counters.json хранит верхнюю границу уже выданных номеров и должен попадать в git, чтобы удалённый номер не выдавался повторно.

Как это выглядит в работе

Создали задачу на ветке — она называется по семени, и sync честно говорит, что номер выдал бы, но не здесь:

$ ls tasks/
TASK-wcvfh1zc-add-healthcheck.md

$ /polisade:sync --apply          # на ветке feat/healthcheck
"numbering": {
  "assigned": [],
  "pending":  [{ "from": "TASK-wcvfh1zc", "to": "TASK-001", ... }],
  "on_trunk": false,
  "why": "ветка 'feat/healthcheck', а номера выдаются только на 'main'"
}

Работа доехала до основной ветки — тот же sync выдаёт номер, переименовывает файл и переписывает id:, оставляя seed: на месте:

$ /polisade:sync --apply          # на main
"assigned": [{ "from": "TASK-wcvfh1zc", "to": "TASK-001",
               "path": "tasks/TASK-001-add-healthcheck.md", "how": "git mv" }]

$ head -3 tasks/TASK-001-add-healthcheck.md
id: TASK-001
seed: wcvfh1zc          # не изменился и не изменится

Что едет за номером

Машинные ссылки — parent:, depends_on:, blocks:, related:, realizes_requirements:. Их сравнивают с ID, а не читают глазами, поэтому sync переводит их на новый номер, включая составные формы вроде SPEC-<семя>.FR-001. Совпадение только по целому токену: TASK-k7m2q4xzx не тронут, когда номер получает TASK-k7m2q4xz.

Что не едет — и это намеренно

Проза внутри артефактов остаётся с семенем. Ссылку, сделанную до нумерации — сообщение коммита, заголовок PR, строку в переписке, — переписать нельзя. Текст человека верен ровно потому, что семя не двигалось. Разрешить такую ссылку можно вызовом polisade_id.py resolve <семя> из каталога скриптов установленной сборки — печатает текущий ID и путь.

Ограничение нумерации. Два клона, которые выдали номера на своих основных ветках до обмена изменениями, могут получить одинаковый номер. После объединения sync обнаруживает duplicate_ids и может перенумеровать более поздний артефакт, если выбор однозначен. Постоянный идентификатор сохраняется. Координируйте выдачу номеров и коммитьте счётчики.

doctor проверяет постоянные идентификаторы: дубликаты, пропущенное поле seed, несовпадение с ID и выход пути за границу проекта. Неразрешённую проблему сначала исправляют; нумерация не должна скрывать её.

Два формата спецификации — и где живёт change-spec

Речь только о внутреннем формате файла спецификации; путь и имя от формата не зависят (на имя влияет ключ трекера — см. каталог артефактов). Формат выбирается один раз настройкой settings.experimental.changeSpec.

Классический — по умолчанию

Спецификация в духе ISO-29148: контекст, функциональные и нефункциональные требования, ограничения. Шаблон — docs/templates/spec-template.md. Задачи по ней получаются обычные, без координат.

change-spec opt-in, экспериментально

Спецификация «от кода»: описывает дельту, а не систему целиком. Шаблон docs/templates/change-spec-template.md, в заголовке файла появляется kind: change-spec. Шесть секций: что и зачем · дельта требований · локализация в коде · контракты · дельта интента (ADR, качество, глоссарий) · открытые вопросы.

Что включено в новом проекте. Ничего из экспериментального: в .state/PROJECT_STATE.json все четыре ключа settings.experimental стоят в false. По умолчанию вы идёте классическим путём — обычная спецификация и дизайн-пакеты, без корпуса. change-spec — это осознанное включение, а не текущее состояние по умолчанию.
  • Что меняется дальше по цепочке. По change-spec команда tasks делает задачи с координатами (kind: coordinate-task): файл и символ прописаны заранее, и реализация их не ищет свободно, а подтверждает.
  • Линтеры разные — это важно. polisade_spec_lint.py проверяет только change-spec и координатные задачи; классическую спецификацию он намеренно пропускает («legacy-spec, skipped»). Форму классических артефактов проверяет polisade_lint_artifacts.py, и требования там жёсткие: у каждого FR нужен блок **Statement:** в форме EARS и сценарий Given/When/Then — иначе ошибка. Формулировка проверяется по английским шаблонам (The … shall …, When …, the … shall …) — ровно так написан каркас в поставляемом шаблоне спецификации; русская фраза линт не пройдёт.
  • Что выбрать. Начинайте на классическом — он ничего дополнительного не требует. change-spec имеет смысл там, где правки точечные и нужно жёстко ограничить радиус изменений; экспериментальным он помечен намеренно и по умолчанию выключен.

tasks		Из координат секции 3 собираются координатные задачи. Линт делает обязательными три вещи: coordinates (файл + символ), requirements (ссылки на FR) и сценарий Given/When/Then. Координата на несуществующий файл — ошибка, если он не объявлен как создаваемый. Пересечение координатных файлов между задачами одной спецификации даёт предупреждение: подсказка переразбить.tasks/TASK-NNN-*.md, kind: coordinate-task
Реализация
implement		Режим меняется на верификацию координат: свободного поиска нет, бюджет навигации — один–три обращения, правки только внутри координат. Понадобилось выйти за них — нужен явный повторный проход локализации с пометкой в списке целей; молча расширять объём нельзя. Когда формат уместен

Правки точечные и по существующему коду; нужно жёстко ограничить радиус изменения; вы работаете более дешёвой моделью и хотите заменить её свободный поиск заранее выписанными координатами; важно видеть в спеке, что именно поменяется в коде.

Когда не стоит

Новый модуль с нуля — координат ещё нет, дельта описывает пустоту. Первое знакомство с инструментом — формат добавляет требований и остановок. Проект, где спецификация нужна как документ для людей, а не как задание на правку: для этого и сделан классический формат.

Архитектурная документация: два пути и в чём разница

Оба пути делают одни и те же документы — C4, модель данных, API, глоссарий, решения. Разница в том, где они лежат и что происходит со второй спецификацией.

design — пакет на каждую спецификацию

Для SPEC-001 создаётся каталог DESIGN-001-slug/ и всё нужное складывается внутрь него. Для SPEC-002 — новый каталог со своим набором. Каждый пакет самодостаточен и ничего не знает о соседях.

docs/architecture/
├── DESIGN-001-export-pdf/    ← своя копия глоссария,
│   ├── api.md                  своя схема контейнеров,
│   ├── data-model.md           свой кусок модели данных
│   └── glossary.md
└── DESIGN-002-notifications/ ← и снова своя копия того же
    ├── api.md
    ├── data-model.md
    └── glossary.md

Что хорошо: просто, предсказуемо, работает во всех сборках без флагов. Для нового модуля с нуля — рабочий путь.

Что плохо: общесистемные вещи — термины, границы контекстов, верхний уровень C4, решения — оказываются размножены по пакетам. Через пять спецификаций у вас пять глоссариев, и они начинают расходиться. Единого ответа на вопрос «как устроена система» нет: есть пять ответов про пять кусков.

design-corpus — один общий корпус включается явно

Каталог docs/architecture/ — единственное описание системы, и каждая спецификация его дополняет, а не копирует. Новый термин добавляется в общий глоссарий, новая сущность — в общую модель данных, новая связь — в общую схему.

docs/architecture/          ← одна система — одно описание
├── glossary/terms/          ← термины, по файлу на термин
├── model/entities/          ← сущности данных
├── contracts/openapi.yaml   ← общий контракт API
├── decisions/               ← ADR
└── INDEX.md                 ← навигатор по корпусу

docs/specs/SPEC-001/
└── changeset.yaml           ← «что эта спецификация добавила и изменила»

Удобная аналогия: спецификация — это коммит, корпус — рабочая копия. Вы читаете актуальное состояние в одном месте, а историю «кто что принёс» — по списку изменений каждой спецификации.

Что хорошо: общие сведения собраны в одном месте, что упрощает их обновление. Согласованность содержания всё равно нужно проверять.

Что плохо: режим экспериментальный. Содержимое помечается как предположение или пробел — метки «подтверждено» не бывает; первый успешный прогон переводит проект в режим корпуса; автоматического переноса обратно в пакеты нет. Есть предпросмотр --dry-run.

Что выбрать. Одна-две спецификации или новый модуль с нуля — оставайтесь на design, разницы вы не почувствуете. Спецификаций становится много и вы ловите себя на том, что правите один и тот же термин в трёх пакетах — это сигнал переходить на корпус. Переход не автоматический, но с версии 3.8.0 это одна команда — /polisade:design-corpus --adopt (по-русски: «переведи архитектуру на корпус»). Она находит все пакеты DESIGN-NNN-*/, показывает план и ничего не пишет до вашего подтверждения. В плане четыре класса файлов: переносится как есть, сворачивается моделью, не нашлось дома (решаете вы), индекс пакета. Класс «как есть» сегодня пуст, и команда говорит это вслух: у артефактов пакета нет дома один-к-одному, поэтому «перенесено 0» — результат, а не сбой. Настоящая работа — свёртка: модель по одному раскладывает содержимое пакетов по местам в корпусе. Конфликт (файл в корпусе уже есть и отличается) останавливает прогон целиком, и выбор «пропустить или перезаписать» делаете вы. Пакетов нет — команда так и скажет, что переводить нечего.
Доступность корпуса. В v3.8.15 design-corpus доступен в Claude Code, Qwen, GigaCode и opencode. Сначала включите /polisade:migrate --enable=designCorpus --apply, затем вызовите /polisade:design-corpus SPEC-NNN --dry-run. Для переноса существующих дизайн-пакетов используйте --adopt и просмотрите план. Сборка GigaCode читает необходимые справочники из копии в проекте. Качество синтеза зависит от модели; наличие команды во всех сборках не означает одинакового качества результата.
Источник истины для статуса — сам файл артефакта. В реестре .state/PROJECT_STATE.json лежит производная проекция. Правили Markdown руками? Запустите /polisade:sync --apply — реестр пересоберётся из файлов. Без --apply команда показывает расхождения и не применяет их к документам и реестру; локальный отчёт при этом может быть записан. Обратный порядок (правка реестра руками) почти всегда заканчивается расхождением.

design-corpus — вливание изменения в архитектуру opt-in, экспериментально, все CLI

аналог «архивации» изменения: спецификация — коммит, корпус — рабочая копия

Это ответ на вопрос «что делать, когда спецификаций стало десять, а архитектура должна быть одна». Вместо отдельного пакета на каждую спецификацию изменение применяется к единому живому корпусу docs/architecture/: общие сведения (контекст, контейнеры, глоссарий, модель данных) собраны в одном месте, а каждая спецификация добавляет тонкий changeset.yaml со списком «создано / изменено / решено» и рёбрами на требования.

Команда синтезирует docs/specs/SPEC-NNN/changeset.yaml — тонкий список «создано / изменено / решено» со ссылками на требования (целевая раскладка предполагает рядом и саму дельту требований). Каталог корпуса накапливает производные навигаторы (INDEX.md, manifest.yaml, trace.json) и логи прогонов runs/ARCHRUN-NNN.md. Есть режим --dry-run: показать разницу, ничего не применяя. Существующие пакеты DESIGN-NNN-*/ сами при этом не переезжают, но переезд доступен отдельной командой — scripts/polisade_migrate_silo.py (предпросмотр по умолчанию, запись через --apply, вся запись — через примитив корпуса).

Если прогон остановился с вопросом, он оставляет лог ARCHRUN-NNN, а после вашего ответа продолжается только через --resume=<id прогона>: статус «готово» у такого лога означает «нужен возврат к прогону», а не «работа выполнена».

Шаг включается командой /polisade:migrate --enable=designCorpus --apply и по умолчанию выключен. Корпус строится best-effort сильной моделью: содержимое помечается как предположение или пробел — метки «подтверждено» в корпусе не бывает вообще, — и детерминированных проверок целостности здесь нет. Если корпус не включён — ничего страшного: дизайн-пакеты остаются отдельными пакетами на каждую спецификацию, а расхождения помогает искать следующий шаг.

Сверка и обслуживание скрипт

reconcile-docs · sync · doctor · проверка дрейфа в CI

reconcile-docs — сверка архитектурного корпуса с кодом. Она разделена на две части: механически проверяется только разрешимость ссылок корпуса (существует ли файл, попадает ли диапазон строк в его размер, встречается ли символ), а сами расхождения ищет модель. Отсюда прямая оговорка, которая печатается в каждом выводе: пустой список означает «модель ничего не заметила», а не «архитектура соответствует коду». Ничего не применяется автоматически — правка корпуса это отдельный подтверждаемый шаг. Можно сузить объём: reconcile-docs SPEC-001 или reconcile-docs src/orders. Отдельным шагом идёт детерминированная сверка полей спек-артефакта с вашим эталоном — JSON Schema, OpenAPI, AsyncAPI либо Markdown-файлом с блоками ```json / ```yaml (обычная таблица «поле / тип» не подойдёт); это линт формата на входе, а не вердикт о корпусе.

Рядом работает второй, детерминированный механизм — проверка дрейфа (scripts/polisade_drift_gate.py): машинно сверяет пути из api.md с роутами в коде и ER-диаграмму из data-model.md со схемой БД. И он блокирующий: запускается не только в CI, но и внутри реализации перед созданием PR — при расхождении задача уходит в waiting_pm. Единственный легальный способ подавить находку — файл-исключение в docs/waivers/: обязательны status: active, дата expires (после неё гейт снова краснеет) и точные ключи подавляемых находок; создавать его агенту запрещено.

Здесь же уместно дописать knowledge.json тем, что выяснилось по ходу: новые паттерны, грабли, решения. Это то, что переживает сессию и делает следующую работу лучше.

выходсписок дрейфа, актуальный реестр, обновлённая память проекта
Чего в цикле нет — и это стоит знать сразу. Артефакты не перемещаются автоматически в отдельный архив: всё остаётся на своих местах, история не прячется в отдельный каталог. Статусы при этом разные: задачи закрываются в done, а бриф, спецификация и дизайн-пакет доходят до accepted и живут дальше как действующие документы. В режиме корпуса шаг 9 добавляет изменение в общее описание архитектуры; спецификация сохраняет описание соответствующего изменения. Если корпус выключен, роль «единого места» играют дизайн-пакеты и ADR, а роль сторожа — шаг 10.
Схема · автономный цикл

Цикл одной задачи

Это ядро процесса. Цикл не прерывается на падающих тестах и замечаниях ревью — их агент чинит сам. Он прерывается только там, где нужно решение человека. Нумерация здесь своя: пять фаз ниже — это внутренность шага 7 «Маршрута по шагам», а не продолжение его шкалы.

Подготовка, реализация и PR

При включённом ветвлении инструмент task-worktree готовит ветку и дерево задачи до реализации. Для родителя PLAN используется ветка plan/PLAN-001-TASK-007-slug; задачи одного FEAT, BUG, DEBT или CHORE обычно используют общую ветку родителя. Путь возвращает инструмент, агент использует его в дальнейших шагах.

implement предусматривает локализацию, тесты и код, регрессию и настроенные проверки проекта. Перед push инструмент повторно проверяет основную ветку. При неподтверждённом push задача останавливается с причиной; PR после такого отказа не создаётся. На недоступный служебный скрипт нельзя отвечать обходом через обычный git push.

Создание PR учитывает уже открытый PR для той же ветки и базы. Если сведения сервера нельзя прочитать, это ошибка проверки, а не доказательство отсутствия PR.

Кто выполняет ревью

В Claude Code выбор задаётся settings.reviewer. В Qwen, GigaCode и opencode ревью PR выполняет отдельный субагент с собственным контекстом; флаг self там принимается для совместимости.

Режим в Claude CodeПоведение
autoCodex CLI, если доступен и прошёл проверку идентичности; иначе отдельный запуск текущего CLI, если доступен.
externalТолько Codex CLI; если недоступен, ревью останавливается.

Отдельный контекст снижает влияние истории реализации, но не гарантирует независимость суждений модели. Проверка идентичности Codex сверяет вывод версии, а не криптографическую подпись программы. Внешний CLI действует в пределах своих разрешений.

Что изменилось в ревью v3.8.15

  1. До запуска ревьюера polisade_review_pr_guard.py проверяет статус задачи, находит её рабочее дерево и запускает testing.testCommand из технического контекста этого дерева.
  2. Тот же инструмент записывает готовое задание в .polisade/tmp/review-brief-TASK-….md. Агент передаёт ревьюеру путь к файлу. Контрольная строка задания должна вернуться в отчёте; несовпадение требует остановки.
  3. Ревьюер читает результат тестов, анализирует изменения и публикует оценку. Он не запускает тесты повторно и не переключает ветки. Повтор прогона предусмотрен перед второй итерацией после исправлений.
  4. При оценке не ниже 8 из 10 сценарий ревью допускает merge; при более низкой оценке предусмотрены исправления и повторная проверка. После двух неудачных итераций требуется решение человека.

Строка результата различает успешный прогон, ошибки, отсутствие команды и устаревший прогон. Нет рабочего дерева, неподдерживаемая форма команды или обрыв по таймауту — основание считать тесты непроверенными. Результат хранится в .polisade/tmp/review-tests-TASK-….json. Проверка свежести учитывает коммит и изменения отслеживаемых файлов; новые неотслеживаемые файлы в этот отпечаток не входят.

Контрольную строку задания сверяет модель. Сам факт её совпадения не доказывает полноту ревью. Проходной балл также не заменяет результат CI и правила защиты ветки.

Слияние выполняет VCS-инструмент. Сценарии review-pr и continue используют pr-merge --task. При подтверждённом слиянии инструмент записывает done; при отказе или неподтверждённом результате — причину и остановку в waiting_pm. Повтор merge блокируется до явного признания причины человеком; новые коммиты сами этот запрет не снимают. Не нужно повторять merge другим способом.

На GitHub используется squash; в Bitbucket Server флаг --squash принимается без выполнения squash. В v3.8.15 запись done может остаться отдельным локальным коммитом ветки задачи и не попасть в основную ветку, поскольку PR уже смержен. Инструмент отклоняет push ветки на таком завершающем коммите. Состояние PR на сервере и результат записи статуса проверяйте отдельно.

Какой режим выбрать

/polisade:implement TASK-NNN ведёт одну задачу по подробному протоколу и предусматривает остановку перед merge. Для первого пилота и чувствительных изменений используйте его и явно договоритесь, кто разрешает слияние. Самостоятельный вызов /polisade:review-pr включает собственный сценарий, который может завершиться автоматическим merge.

/polisade:continue работает по приоритетам и зависимостям, возобновляет начатое и автоматически сливает прошедшие проверку PR. Когда готовых задач нет, может перейти к подготовке спецификаций и задач из других готовых артефактов. Объём запуска определяется всем содержимым ready, а не только очередью TASK.

Протоколы различаются. У continue собственный, более короткий цикл. Он не исполняет все остановки implement, в частности приёмку в режиме block, API-гейт и проверку дрейфа. На старте он сообщает о применимых невыполняемых проверках и повторяет это в итогах. Если эти проверки обязательны, используйте implement и закрепите их в CI.

Тесты и проверки проекта

Для implement по умолчанию задана стратегия tdd-first: сначала падающие тесты отдельным коммитом, затем реализация. В test-along код и тесты пишутся вместе; этот режим также применяется, если отдельный запуск тестов задачи технически невозможен.

Регрессия запускает testing.testCommand, проверка типов и линтер — соответствующие команды из knowledge.json. Если команда не задана, проверка пропускается с предупреждением. Таймаут не означает успешный прогон; сценарий реализации может продолжить создание PR с неполной проверкой.

Дополнительные проверки проекта — security, совместимость API, миграции и производительность — включаются объявленными командами. Их условия и последствия различаются: API-гейт может остановить создание PR, а оставшиеся находки других проверок после попыток исправления могут быть переданы в ревью. Название режима block не означает одинакового поведения всех проверок. Точный контракт описан в настройках и публичном справочнике.

Остановка, продолжение и отмена

Сессию можно прервать средствами CLI. Сохранённые файлы и коммиты останутся, но незавершённый шаг придётся проверить: это восстановление по состоянию репозитория, а не продолжение процесса с точной контрольной точки. Начните с state и проверьте рабочие деревья.

Для отмены закройте PR и явно зафиксируйте исход cancelled с причиной через предусмотренный сценарий работы с задачей. До удаления worktree сохраните нужные изменения. git worktree remove без --force откажется удалять дерево с несохранёнными изменениями. Отмена и возврат в ready — разные решения; не подменяйте одно другим.

Совместное использование ветки несколькими задачами требует внимания к составу PR и уже смерженным коммитам. Если нужен отдельный PR на каждую задачу, планируйте работу через PLAN. Не считайте отсутствие переключения основной копии гарантией изоляции: проверяйте путь дерева из ответа инструмента.

Навигация по коду

Локализация: как определить места правки

В подробном протоколе implement перед правками предусмотрена локализация: термины из задачи → символы → места использования → список целей. Поиск выполняют инструменты, а выбор запросов и интерпретацию результатов делает модель. Соблюдение порядка задаётся инструкцией.

Что делает агент

  • Берёт 2–5 ключевых терминов из задачи — имена классов и функций, поля, эндпоинты, тексты ошибок — и ищет их по исходникам.
  • По найденным символам проходит места использования. Если правка меняет контракт или сигнатуру, обязан перечислить всё, что от неё сломается.
  • Печатает список целей и дальше правит только по нему. Пустой результат поиска — сигнал неверного термина, а не разрешение править наугад.

Артефакт локализации

Печатается в вывод сессии до первой правки. В тело PR он не попадает — если хотите видеть его в PR, попросите агента вставить блок в описание:

─────────── LOCALIZATION (TASK-002) ───────────
tool: grep
targets:
  - file: src/reports/export.py
    symbols: ReportExporter.to_pdf
    why: FR-003 — точка сборки файла
  - file: src/api/routes/reports.py
    symbols: export_report
    why: новый параметр format
refs_checked: grep(to_pdf), grep(export_report)
out_of_scope: src/reports/csv.py (формат не меняется)
───────────────────────────────────────────────

Правки разрешены только по списку targets. Появилась новая цель — нужен явный повторный проход с пометкой в списке; молча расширять объём нельзя.

Почему это важно для вас. Список целей помогает оценить объём до правок и заметить его расширение. Он выводится в сессию, поэтому при необходимости сохраните его в PR отдельно. Результат поиска по исходникам не является полной картой зависимостей и не гарантирует, что найдены все затронутые места.
Приёмка

Приёмка: ожидаемый результат подтверждает человек

Одна приёмочная пара — описание ожидаемого поведения и одна команда его проверки. Модель предлагает черновик, ответственный человек подтверждает каждый пункт. Набор хранится в acceptance/ACCEPTANCE.md.

1. Подготовить и подтвердить критерии

/polisade:acceptance author
/polisade:acceptance author AC-003

Команда читает требования из SPEC или FEAT, задачи, README и технический контекст. Если исходных требований нет, начинает с интервью. За один проход предлагает до семи пунктов, затем показывает каждый целиком: формулировку, связь с требованием, затронутые файлы и команду проверки.

Ответьте «подтверждаю», «изменить» или «убрать». Молчание не является согласием. Команда принимает режим и необязательный номер пары; отдельного позиционного аргумента SPEC у неё нет. Если спецификаций несколько, укажите нужную обычной фразой и проверьте поле requirement.

## AC-001 — Пустой отчёт отклоняется с кодом 422

- requirement: SPEC-001.FR-003
- target_files: src/reports/export.py
- ratified_by: PM
- ratified_at: 2026-10-15

```bash
python3 -m pytest tests/acceptance/test_export_pdf.py::test_empty_report_422 -q
```

Это пример формата. Канонический шаблон выводит polisade_acceptance.py template. Поле ratified_by обозначает ответственного человека; линтер лишь предупреждает о его отсутствии, поэтому формальная успешность линта не доказывает подтверждение.

2. Проверить формат и сохранить базу

После записи выполняются линт и фиксация хешей пар и файлов проверок. База .state/acceptance-baseline.json должна быть закоммичена: иначе у коллег и в CI не будет исходного состояния для сравнения.

Проверка возвращает 0 при успехе и ненулевой код при нарушении ожидаемого поведения. Заведомо успешные конструкции вроде || true отвергаются линтом. Если команда не называет тест-файлы явно, укажите instruments — файлы тестов, фикстур или конфигурации, изменения которых нужно отслеживать.

Критерии полезно записать до реализации. Если тест-файла ещё нет, ошибка запуска не проверяет нужное поведение. Подготовьте исполняемый тест и убедитесь, что он падает по ожидаемой причине. Режим ремонта не предназначен для создания себе новых проверок.

3. Выполнить проверки

/polisade:acceptance run
/polisade:acceptance run AC-001

Сначала проверяется формат набора. При ошибках линта запуск отклоняется. Каждая команда выполняется отдельно, по умолчанию с таймаутом 300 секунд. Результат сохраняется в .state/acceptance-report.json; изменения относительно базы отмечаются отдельно. Таймаут и ошибка запуска означают, что результат не подтверждён.

Для CI доступен режим Python-скрипта run --fail-on-changed: он завершает прогон ошибкой при изменении проверок относительно базы. Если базы нет, возвращается код 2. Этот режим нужно задать явно.

4. Исправить реализацию

/polisade:acceptance repair
/polisade:acceptance repair AC-002

Ремонт запускается по просьбе человека и меняет код по неуспешным проверкам. Предусмотрено не больше трёх раундов. Тест-файлы, фикстуры, конфигурацию запуска и сами критерии ослаблять нельзя. Если хеши разошлись с базой, сначала требуется разобраться с изменением проверок.

Как приёмка связана с реализацией

testing.acceptanceModeПоведение в implement
advise, по умолчаниюПосле регрессии предлагает прогон; не блокирует цикл.
blockВыполняет приёмку. После предусмотренных попыток ремонта оставшиеся ошибки останавливают задачу в waiting_pm.
offПропускает этот шаг.

Если файла приёмки нет, цикл не останавливается даже в block: критерии ещё нужно согласовать. continue не исполняет этот шаг; он сообщает о невыполняемой остановке, а приёмку нужно запускать отдельно или включать в CI.

Где видно состояние приёмки

Раздел в описании PR, комментарий ревью, state и doctor используют polisade_acceptance.py status. Он ничего не тестирует: сообщает о наличии пар, базе, последнем прогоне и его актуальности для текущего кода. Отказ запуска команды состояния должен показываться как «не удалось определить», а не как отсутствие приёмки.

Как читать успешный результат. Он означает, что указанные команды прошли на проверенном коде. Полнота критериев, качество тестов и согласие ответственного человека требуют отдельной оценки. Файлы проверок доступны исполнителю: хеши обнаруживают изменение относительно базы, но не предотвращают его. Проверяйте дифф тестов и храните базу в git.
Устройство исходников

Что где лежит в исходниках — и как это проверить

Публичная поставка содержит текстовые инструкции и скрипты на стандартной библиотеке Python. Ниже — карта публичных исходников проверенного релиза.

Одна команда = один файл инструкции

Каждая команда живёт в skills/<имя>/SKILL.md: YAML-заголовок (name, description, подсказка по аргументам, требования к CLI) плюс алгоритм обычным текстом. Агент читает этот файл и выполняет описанное — никакого скрытого рантайма между ним и моделью нет.

Отсюда два практических следствия. Во-первых, поведение можно прочитать целиком перед запуском: «что именно сделает implement» — можно узнать из инструкции. Фактическое выполнение зависит также от модели и результатов инструментов. Во-вторых, его можно изменить под себя: файл открытый, форк работает как форк.

skills/
├── implement/SKILL.md        # алгоритм реализации одной задачи
├── implement/references/     # длинные протоколы, читаются по ходу
├── continue/SKILL.md         # автономный цикл
├── spec/ tasks/ design/ …    # по одному каталогу на команду
└── init/templates/           # то, что копируется в ваш проект

Изолированные субагенты

Тяжёлые шаги — spec, design, roadmap, tasks, implement, review-pr — запускаются отдельными субагентами с собственным контекстом. Смысл двойной: контекст не засоряется прошлыми шагами, а ревью не видит «мыслей» реализации и потому оценивает результат, а не намерение.

Четыре сборки из одного источника

Claude Code получает плагин как есть. Сборки для Qwen, GigaCode и opencode собирает конвертер tools/convert.py из тех же skills/*/SKILL.md; между сборками есть различия в способе выполнения: имя контекст-файла, формат имён команд (в opencode они плоские), способ независимого ревью, флаги неинтерактивного запуска. Точечные отличия поведения задаются оверлеями tools/qwen-overlay/ и tools/opencode-overlay/.

Что именно умеет каждый внешний CLI и с какими аргументами он вызывается — в одном файле cli-capabilities.yaml. Там же список команд, которые дополнительно публикуются как «навыки» для распознавания обычных фраз.

Где источник истины

  • Статус работы — заголовок самого файла артефакта. Реестр .state/PROJECT_STATE.json — производная проекция, её пересобирает sync.
  • Контекст проекта — .state/knowledge.json: стек, команды тестов, паттерны, решения, словарь. Едет в git и переносится между людьми и машинами — вместе с отметкой о выданных номерах, базой приёмки и журналом сессий (что именно и почему — в разделе про командную работу). Заполняется автоопределением при init, интервью в spec и design, и дописывается реализацией по итогам задач; субагенты обязаны брать команды именно отсюда, а не изобретать свои.
  • Схема всех полей состояния, настроек и переменных окружения — docs/config-reference.md.
  • Требования — нумерованные FR и NFR в спецификации; на них ссылаются задачи, ревью и приёмка. Это тот самый «шов», по которому проверяется, что реализовано именно заказанное.
  • Формат приёмки — то, что печатает polisade_acceptance.py template; линт проверяет ровно его.

Границы и ограничения

Что проверяет инструмент и что проверяет команда

Скрипты проверяют конкретные свойства файлов, статусов и ответов сервера. Инструкции задают порядок действий модели. Эти механизмы полезны вместе, но не дают гарантии качества всего результата.

Проверки в поставке

  • Формат документов, идентификаторы и часть связей между требованиями и задачами.
  • Прогон приёмочных команд и сравнение их хешей с базой.
  • Подтверждение push по удалённому SHA.
  • Подготовка дерева задачи и проверки основной ветки.
  • Проверка допустимого состояния перед ревью, запись отказа merge и блокировка повтора до решения человека.
  • Подготовка задания ревьюеру и результата тестов перед ревью.

Что требует отдельной проверки

  • Полнота требований и соответствие реализации намерению заказчика.
  • Качество тестов: успешный прогон не показывает, были ли проверки ослаблены.
  • Соблюдение моделью правил, которые заданы только текстом инструкции.
  • Права доступа и обработка данных моделью и внешним ревьюером.
  • Актуальность отчётов для текущего кода и фактический набор проверок выбранной команды.
  • Полнота общего архитектурного корпуса и выводов сверки документации с кодом.

Приёмочные файлы доступны исполнителю на запись. Хеши позволяют обнаружить изменение относительно сохранённой базы, но не предотвращают его и не удостоверяют личность подтвердившего. Рабочее дерево отделяет файлы ветки, но не создаёт песочницу. Сессия восстанавливается по файлам, без точной контрольной точки исполнения.

Для командной работы назначьте владельцев требований и тестов, проверяйте изменения проверок в PR, включите независимый CI и защиту основной ветки. В среде с требованиями к аудиту заранее определите, какие журналы и подтверждения нужно сохранять дополнительно.

Включите проверку дрейфа в CI — рецепт уже лежит в .github/workflows/ после init. И допишите в knowledge.json то, что выяснилось: «коды генерируем в сервисе, не в роуте», «в тестах используем httpx-клиент FastAPI». Следующая фича начнётся с этого знания, а не с нуля.

Практика 11. Память проекта пополняется после каждой заметной работы. Она переносится между сессиями вместе с документами и кодом; поддерживайте её в актуальном состоянии.

Что осталось в репозитории

backlog/features/FEAT-001-shorten-link.md
docs/plans/PLAN-001-shorten-link.md
docs/specs/SPEC-001-shorten-link.md            # FR-001…004, NFR-001
docs/architecture/DESIGN-001-shorten-link/     # api.md, data-model.md
docs/architecture/decisions/ADR-001-sqlite-as-storage.md
acceptance/ACCEPTANCE.md                       # 4 ратифицированные пары
tasks/TASK-001…004-*.md                        # состояние проверяем с учётом рабочих деревьев
src/shortlink/                                 # код
tests/                                         # тесты задач + приёмочные
.state/knowledge.json                          # память проекта
4 смерженных PR с комментариями ревью и оценками

Через полгода на вопрос «почему код 7 символов и почему SQLite» отвечают NFR-001 и ADR-001, а не чья-то память.

Что дальше

  • Вторая фича — быстрее: feature → tasks → continue. Спецификация нужна не всегда, память проекта уже заполнена.
  • Появилась статистика переходов? Это уже новая схема данных — значит снова spec, и ADR о том, где хранить счётчики.
  • Спецификаций стало много? Посмотрите на режим единого живого корпуса (шаг 9 маршрута): архитектура остаётся одна на систему вместо отдельного пакета на спецификацию.
  • Работаете в команде? Зафиксируйте письменно: когда обязателен PRD, кто мержит после implement, кто отвечает на вопросы агента. Без этой договорённости процесс расползается быстрее, чем от любых технических причин.
Второй кейс

Кейс: доработка существующего проекта — экспорт отчёта в PDF

Учебный пример изменения API и хранения файлов. Ниже — последовательность команд и выдержки из документов с условными идентификаторами и результатами. Полные требования и проверки нужно согласовать для своего проекта.

Шаг 1. Интент

/polisade:feature "Нужен экспорт отчёта в PDF из карточки отчёта"

Появился бриф. Размер оценён как M, поэтому фреймворк спрашивает, нужна ли спецификация — отвечаем «да», работа меняет публичный API.

created: backlog/features/FEAT-001-export-pdf.md   status: ready
─────────────────────────────────────────────────────────────
id: FEAT-001
title: "Экспорт отчёта в PDF"
size: M
problem: отчёт выгружается только в CSV, для согласования нужен печатный вид
scope: кнопка в карточке отчёта, генерация PDF, единый шаблон; способ выполнения уточнить в SPEC
out_of_scope: массовая выгрузка, подписи, водяные знаки
open_questions:
  - хранить ли готовый файл или генерировать каждый раз

Шаг 2. Спецификация

/polisade:spec FEAT-001

Агент читает knowledge.json, уточняет хранение файла и способ генерации. В этом примере человек выбирает фоновое задание; решение отражается в спецификации и ADR.

created: docs/specs/SPEC-001-export-pdf.md   status: ready
─────────────────────────────────────────────────────────────
FR-001  POST /api/reports/{id}/export?format=pdf возвращает 202 и id задания
FR-002  готовый файл доступен по GET /api/exports/{job_id} в течение 24 часов
FR-003  пустой отчёт не даёт пустой PDF, а завершается ошибкой 422
NFR-001 отчёт до 50 страниц генерируется не дольше 10 секунд
Если бы технический контекст был пуст, а стек неизвестен — команда обязана остановиться и спросить, а не «предположить Python и FastAPI».

Шаг 3. Дизайн-пакет по содержанию

/polisade:design SPEC-001

Работа добавляет асинхронное задание и новый контракт — значит след стоит оставить. Генерируются только релевантные файлы.
